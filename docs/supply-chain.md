# Verifying what you installed

A security scanner is exactly the kind of package worth compromising: it runs in CI, it reads your
whole source tree, and people trust its output. So the release pipeline is built to let you check
that the thing you installed is the thing this repository built — without trusting this page.

Nothing here needs a key from us. Every signature is produced by GitHub's OIDC identity for the
workflow, so what you verify is *which workflow, at which commit, built these bytes* — not
"someone who had our private key said so."

## 1. Build provenance — what built it, from which commit

Every release attaches [SLSA build provenance](https://slsa.dev/provenance) to the wheel and the
source distribution.

```bash
pip download secaudit-kit --no-deps --no-binary :none: -d /tmp/verify
gh attestation verify /tmp/verify/secaudit_kit-*.whl --repo mtvrkan/secaudit
```

A pass tells you the file was produced by `release.yml` in this repository, at a specific commit,
by a specific workflow run. A failure — including *no attestation found* — means the file did not
come from that pipeline, whatever the index says about it.

## 2. SBOM attestation — what is inside it

The release also attaches a CycloneDX SBOM, bound to the same artefact digest:

```bash
gh attestation verify /tmp/verify/secaudit_kit-*.whl \
  --repo mtvrkan/secaudit --predicate-type https://cyclonedx.org/bom
```

The SBOM is short, and that is the point rather than an omission: `secaudit-kit` declares **no
runtime dependencies**, and `scripts/assert_no_runtime_deps.py` asserts that against the built
wheel — not against the manifest — on every release. The SBOM is that same fact in the format your
tooling reads.

It is generated by the tool being released (`secaudit kit --format cyclonedx`), which is
deliberate: an SBOM produced by a different tool than the one shipped is one more thing that can
disagree with itself.

## 3. PyPI trusted publishing — no token to steal

Uploads use OIDC trusted publishing, so there is no long-lived PyPI token stored in this
repository to leak or rotate. The publish job is bound to the `pypi` environment, which is also
where a required-reviewer rule belongs.

> **Naming an environment in a workflow does not by itself require approval.** GitHub creates a
> missing environment on first use with no protection rules and the job publishes straight
> through. The gate is a repository setting: *Settings → Environments → pypi → Required
> reviewers*. This is on the launch checklist (`.claude/LAUNCH-CHECKLIST.md`) because it is not
> done yet.

## How the pipeline is arranged, and why

| Job | Holds | Why it is separate |
|---|---|---|
| `validate` | nothing | Re-runs every gate **on the tagged commit**. A green run on `main` is not evidence about a tag — the tag can point elsewhere. |
| `build` | nothing | Builds, asserts zero runtime deps against the artefact, smoke-tests the wheel in a clean venv, emits the SBOMs. |
| `attest` | `id-token: write`, `attestations: write` | Signs. The build never holds a token that can vouch for its own output. An attestation binds to the artefact digest, so signing a downloaded copy signs the same bytes — the separation is free. |
| `publish` | `id-token: write` | Uploads. Bound to the `pypi` environment. |

Every action is pinned to a **resolved** commit SHA. Each was looked up through the GitHub API
rather than written from memory — an unverified 40-hex string is worse than a tag: unverifiable,
authoritative-looking, and a build failure at the worst possible moment. To re-resolve after a
version bump:

```bash
gh api repos/<owner>/<repo>/git/ref/tags/<tag> --jq .object.sha
# If that returns an object of type `tag` it is an ANNOTATED tag, not a commit — follow it:
gh api repos/<owner>/<repo>/git/tags/<sha> --jq .object.sha
```

The workflows are linted by [zizmor](https://github.com/zizmorcore/zizmor) in CI, pinned to a
version. That gate has caught a real mistake here before: `site.yml` held `pages: write` and
`id-token: write` at *workflow* level, so the build job ran holding a token that could publish the
site. Both moved to the deploy job. The `attest` job above is arranged the way it is for the same
reason, learned the same way.

## What is not signed

The container image is not yet signed or digest-attested, and the GitHub Action is consumed by
tag. Both are open — they are named here rather than left for you to discover, because a page
about verification that quietly omits the unverifiable parts is worse than no page.
