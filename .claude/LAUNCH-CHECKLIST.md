# Launch checklist — the steps that need your account, in order

Everything in this repository that can be done by code is done, gated, and pushed. What is left
needs a GitHub or PyPI session, and one item needs money. This page exists so those steps are a
list to work through rather than a thing to remember.

Each item says what it unblocks and what it costs to keep deferring, because two of them have a
real cost that only shows up if nobody writes it down.

## 1. Reserve `secaudit-kit` on PyPI — the only item with a running clock

**Status:** deferred by your own decision on 2026-08-12 ("pypi sonra yapalım"), and that decision
is still fine. But it has a cost worth restating: **a pending trusted publisher does not reserve
the name.** `secaudit-kit` is claimable by anyone until the first upload, and the day someone
takes it is the day this kit needs a different name in every document that mentions it.

The publisher is already configured and was verified field by field:

| PyPI setting | Value |
|---|---|
| Pending project name | `secaudit-kit` |
| Owner / repository | `mtvrkan` / `secaudit` |
| Workflow | `release.yml` |
| Environment name | `pypi` |

**To publish:** push a `v1.0.0` tag. It must match `version` in `kit/pyproject.toml` — the
workflow fails the build if it does not, deliberately.

**To reserve the name without launching:** publish a placeholder version instead. That is a
one-way door of its own (a version number cannot be reused), so it is a real choice, not a
free hedge.

## 2. Require a reviewer on the `pypi` environment

GitHub → Settings → Environments → `pypi` → Required reviewers.

**Naming an environment in a workflow does not by itself require approval.** GitHub creates a
missing environment on first use with no protection and the job publishes straight through. The
workflow comment used to claim otherwise; that was corrected, and this is the step that makes it
true. Do this **before** step 1, not after.

## 3. Make the repository public

A launch decision, not a technical one — and the one that unblocks the next two items.
Everything is ready for it: the license, the disclaimer, the code of conduct, the contributing
guide, the CI badge, and a README whose every number is derived and gated.

## 4. Turn on GitHub Pages

Blocked only by step 3 — Pages on a private repository needs a paid plan. `site/dist/` is
generated by `scripts/gen_site.py` and CI publishes it; nothing else is needed once the repo is
public.

**The deploy job skips itself until then** (`if: github.event.repository.private == false` in
`site.yml`), because before that guard existed it failed on every single push. Unlike step 4b
there is no line to delete — the condition flips on its own the moment the repository is public.
The thing to actually do here is *check that it did*: a job that has only ever skipped has never
been proven, so watch the first push after going public and confirm the deploy ran and the page
is live. A skip and a success are one character apart in a check list and nothing else will tell
you which one you got.

### 4b. Then delete one line from `self-scan.yml`

The self-scan uploads its SARIF to code scanning, which is what actually proves the renderer's
output is *accepted* rather than merely well-shaped. Code scanning on a private repository needs
GitHub Advanced Security, so that step currently carries `continue-on-error: true` — the scan
still gates the build, only the upload is allowed to fail.

**While that line is there, a green run does not prove the upload works.** Remove it once the
repository is public; the first successful run is the proof, and it is the last open item on the
SARIF integration.

**Observed 2026-08-17, and it splits into two claims rather than one.** The run log shows the
upload action reaching `Validating secaudit.sarif` and `Adding fingerprints to SARIF file`, then
failing with `Resource not accessible by integration`. So GitHub's own SARIF validator **accepts
the renderer's output** — that half is proven, on 59 findings from a live self-scan — and
ingestion into code scanning has never happened, which is exactly the half Advanced Security
gates. Say it that way rather than "the SARIF works" or "the SARIF is untested"; both are wrong.

### 4c. And turn CodeQL on

`codeql.yml` is gated behind a repository variable that has never been set, so **the workflow has
never run** — every entry in the run history is a 1-second skip. Settings → Secrets and variables
→ Actions → Variables → `ENABLE_CODEQL` = `true`. Like code scanning above, CodeQL on a private
repository needs Advanced Security, which is why the guard exists.

This step was living as a comment inside `codeql.yml` saying it was *"tracked with the other
launch steps in ROADMAP.md"*, and it was not tracked anywhere — not in the roadmap and not here. A
launch step that only exists inside the file it gates is a launch step nobody performs.

## 5. Point DNS at it

A `CNAME` record for `secaudit` → `mtvrkan.github.io` on `mtvrkan.com`. `site/dist/CNAME` is
generated from `ORIGIN` in `gen_site.py`, so the two cannot disagree.

## 6. Measure the LLM tier — the one open engineering gap

Not a launch blocker, and not free. The enrichment tier is the kit's headline claim and has no
measured number; the harness ships and is one command:

```bash
python3 eval/realvuln/run.py --benchmark ../Real-Vuln-Benchmark \
    --backend anthropic --scanner secaudit-tier1
cd ../Real-Vuln-Benchmark
for r in repos/*/; do python3 score.py --repo "$(basename "$r")" --scanner secaudit-tier1; done
python3 dashboard.py --scanners secaudit-tier1
```

It needs an API key and real spend across 62 repositories. The result belongs on
`eval/realvuln/README.md` labelled as a single observation — a model run cannot be a floor, and
the comparison it invites is with the published general-purpose-LLM baseline (F3 51.7), not with
the 61.2 the deterministic tier scores.

## The copy for each channel is written

Drafts for all six launch channels — Show HN, r/netsec, OWASP Slack, the two plugin directories,
the RealVuln leaderboard PR and the CRA post — are in `.claude/LAUNCH-POSTS.md`, out of `docs/`
because a visitor to the site has no reason to read them and the site generator fails the build on
any `docs/*.md` nothing links.

Two things about that file worth knowing before you open it. It opens with **four conditions that
must be true before any of it is posted**, because each one makes a specific sentence in a draft
false — an unobserved CI badge, an unclaimed PyPI name, a site that has never deployed, and a
`continue-on-error` that means a green self-scan proves nothing. And **nothing gates the figures
in those drafts**: they are prose in a file no check reads, so a round that moves a number leaves
them stale silently. Re-read them against `eval/*/result.json` on the day you post.

## What is deliberately not on this list

**Anything a gate already covers.** The first CI run, the semgrep rule pack validating against
real semgrep, zizmor on the workflows, the packaging manifest, the Python floor, the coverage
floor — all of these run in CI on both Linux and Windows and fail the build when they break.
They are not launch steps; they are the reason the launch steps are short.
