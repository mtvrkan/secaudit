**Now** is a login this engine could not read because the project never wrote one. Django ships
`LoginView` and `PasswordResetView`, and a project that uses them mounts them in a URL conf:
`path("accounts/login/", auth_views.LoginView.as_view())` is the whole login. Every structural
rule here reads a *function* — its decorators, its body, its helpers — so on this shape there was
nothing to read, and the rate-limit rule stayed silent on eighteen labelled cases of exactly the
flaw it exists to find. `RATELIMIT-PY-AUTHVIEW` reads the URL conf instead, and asks the project
rather than the module whether anything bounds attempts: `django-axes` is an entry in
`INSTALLED_APPS` and a middleware line in `settings.py`, and the file that wires the login never
mentions it.

**22 findings, 12 true positives, 10 false ones — F3 60.5 to 61.1, recall 0.5999 to 0.6067,
precision 0.6577 to 0.6562, labelled traps unmoved at 248.** The ten are worth a sentence,
because "false positive" is the benchmark's word and not a verdict: every one is a Django project
whose login is `LoginView`, whose tree contains no limiter of any kind, and whose sibling
repository — the same application generated by a different model — carries a hand-written label
on the identical line. They are unlabelled, not wrong, and this page counts them against us
anyway, because the alternative is to grade our own findings.

**A real application** is the round before it — what happened when the noise floor finally
contained an application that mounts routes, `Ghost` and `Directus`. This page was unchanged by
it (1057 / 550 / 705, F3 60.5), and the round is on it because of what those two projects found:
**a project's own auth middleware was invisible to the missing-auth rule.** `mw.authAdminApi` is
Ghost's name for its own guard, used 220 times, and no marker list can contain a name a project
invents — so every route carrying it read as unauthenticated. The rule reads the naming
*convention* now (`auth` followed by a capital, which `author` and `authority` do not satisfy),
and Ember's Mirage mock server stopped counting as production code. Together: **1,252 findings
to 1,119, High+Critical 376 to 243**, with the thirteen previously-measured trees unchanged to
the digit.

**Vendored directories** is the round before it, which stopped reading a copied-in library as
twelve files of application source. `is_vendored_asset` decided per file, and on `static/js/foundation/` that was wrong

`engine._is_vendor_drop` asks the directory instead: two release-bannered files in one directory
make the directory a drop, and it never applies to a file the scanned project's own manifest
publishes.

**HTML concatenation** is the round before it, and it was measured somewhere else and paid for
here. `SEC-JS-HTML-CONCAT` reports HTML

What it bought is on the corpus it was diagnosed from: [CVEfixes](../cvefixes/README.md)
JavaScript **11.5% → 18.1%**, TypeScript **6.0% → 9.0%**, headline **6.7% → 8.2%** — and the
**sealed** slice moved further than the unsealed one, which is the shape a rule that was fitted
to its labels does not produce. This page is where the bill is shown; that page is where the

Twenty of those 22 findings sit in one library — `static/js/foundation/foundation.*.js`, an
unminified third-party drop in a Django app's static directory. `foundation.js` itself is
correctly classified as somebody else's release and never opened; its siblings carry no banner of
their own and are read as application code. That is a scoping defect, not a rule defect, and it
is stated here rather than fixed inside a round that is about detection: a vendored library does
not arrive as one file, and `is_vendored_asset` still decides file by file.

**Secure cookie flag** is the round before it, and the two previous rounds read together below.

**Django views** is the round that stopped treating a Django view as public. `_route_of` records no path
for a Django function view or a class-based view, because the framework keeps it in `urls.py` —
and `Route.public_by_design` read that empty string as the site root, which files a handler as
deliberately unauthenticated. Every Django view in this corpus was therefore exempt from the
missing-authentication rule, and the exemption was invisible: it looked like a rule that simply
found nothing. **missing_auth 4 → 7, broken_access_control 1 → 2, at +17 false positives and the
labelled trap count unmoved at 248.** F3 59.5 → 59.7, precision 0.676 → 0.6695.

A second fix was measured in the same round and **rejected**: teaching the principal model to see
`request.user` where it stands, rather than only when it is bound to a local. It is a real gap —
Django's idiom is `filter(owner=request.user)` and the matcher only knew `ast.Name`, so 26 labels
sat in handlers the engine believed had no principal at all. Closing it converted **none** of
them into a finding, cost **+26 false positives, and moved the trap count to 247**. The trap count
is the instrument that separates a false positive from an unlabelled real finding, and it had
never moved before. Reverted.

**The two columns before it need reading together, and the second one is not an engine change at
all.**

**Re-measured** is the previous round, re-run today on the same clone before anything was changed
— the reproduction step this page has taken every round. It did not reproduce. The engine did:
932 findings, no repository differing, byte for byte. The *scorer* returned **273 false positives
where this file published 271**, precision 0.7071 rather than 0.7086, and an F3 on the other side
of a rounding boundary.

The first explanation was that 271 was a phantom, and it was wrong, so it is worth following what
the measurement actually said. `result.json` takes its headline from the benchmark's
`dashboard.json` and its per-repository table from the scorecards, and **the table in the same
committed file already summed to 273**. Re-running the two engines *before* that round from
worktrees settles which half was stale: they emit 930 findings and 271 false positives, exactly
as published. The round that shipped 271 emits **932**, and the two extra findings are
`PROTO-JS-WRITE` on one vendored `static/js` file — the `hasOwnProperty` guard that round removed
on purpose. So the defect is not a number nobody produced. It is **a round that changed the
engine and then republished the previous engine's headline**, because `dashboard.py` was not
re-run after its own `score.py`.

That matters beyond two false positives, because the round's published argument leaned on the
stale figure: it said the change was safe partly because RealVuln's false positives were "271
before and after". They were 271 before and 273 after. The instrument that genuinely did not move
is the labelled trap count — 248 either way — which is the one that can tell a false positive
from an unlabelled real finding, and the argument stands on it. The sentence that quoted the
wrong one is corrected in [`eval/secbenchjs/README.md`](../secbenchjs/README.md).

Nothing compared a published file to itself: check 27 holds the prose to it, check 32 holds it to
the engine, and the third edge of that triangle did not exist. It does now (check 42),
`collect_result.py` refuses to write a file whose two halves disagree, and `run.py` records the
engine digest beside the results it writes so the stamp describes the run rather than the working
tree at collection time.

**Quadratic ReDoS** was the round before it, and on this corpus it too was a cost with no gain:
**+4 false positives, no true positive, precision 0.7071 → 0.7041.** All four are the same regular
expression — `^[^@\s]+@[^@\s]+\.[^@\s]+$`, an email check in four seeded FastAPI applications —
and the new quadratic ReDoS criterion is right about it: a subject of the form `a@a.a.a…a ` walks
a quadratic number of splits before failing. RealVuln labels planted flaws, so a real defect
nobody planted counts against precision here, and this page does not get to have that both ways:
**the number is the number, precision fell, and the round is justified on the other corpus rather
than on this one** — SecBench.js `redos` 11 → 28 of 87. What did not move is the part this corpus
can actually adjudicate: its labelled false-positive traps, 248 before and 248 after.

**The largest recall gain since the second round** is the `pathlib` column, and it came from a
class this page
had written off. `path_traversal` sat at **3 of 39** across two rounds that added nine filesystem
sinks between them, and the conclusion recorded here was that its misses were about which values
the engine believed were attacker-controlled. **That conclusion was wrong, and being wrong it
aimed both of those rounds at the wrong half of the problem.**

Reading all 36 labelled misses line by line says the sources were already right — the engine
reports SSRF, SSTI, XSS and open-redirect in the very same handlers, from the very same route
parameters. What was missing was `pathlib`. This catalog modelled the standard library's entire
filesystem surface as one entry, the builtin `open`, and the code under test writes:

```python
parcel_path = BASE_EXPORT_DIR / packet_ref     # the caller chose packet_ref
data = parcel_path.read_text()                 # the sink takes no arguments at all
```

That shape needed something no sink here had needed before: taint arriving through the
**receiver** rather than through an argument position. Nine added sinks moved nothing because all
nine were more ways to spell `open`, and nobody had checked whether the misses spelled it at all.
`path_traversal` **3 → 22 of 39**, `other` **228 → 268 of 831**, for +59 true positives against
+24 false ones — **precision 0.7084 → 0.7086, which is to say it did not move.**

The **JavaScript round** retired `SEC-JS-PROTO`, gave the ReDoS analysis a JavaScript front end
and started reading `dist/` when a package publishes it. Three repositories moved and netted to
zero: `lets-be-bad-guys` lost 3 false positives as the retired rule stopped firing, and
`fintech-lending` and `vulnerable-tornado-app` gained 1 and 2 from the rules that replaced it.

**The round before it** was a narrowing, and the smallest change on this page: prototype pollution requires
the key to come from something the *caller* passed in, rather than from an object the function
built itself. One false positive removed — `AdminAudit.tsx:18`, `Object.keys(filters)` over
component state — and no true positive lost. Precision **0.7075 → 0.7084**. It is here because it
was named in advance: the rule's own title says *attacker-named key*, that line had a key nobody
outside the function could choose, and a rule that does not do what its title says is a defect
whether or not the aggregate notices.

**It is not free, and the cost is on the other corpus.** The same narrowing moved SecBench.js
from 13 to 12 of 185 labelled prototype-pollution sinks. Two of the three it initially lost were
a defect in the narrowing and are back; the third, `js-extend@0.0.1`, binds its key from the
parameter of an anonymous callback and is a genuine loss. So the round reads: one false positive
removed here, one true positive lost there, 54 unmatched findings removed on the JavaScript
corpus. Stated on this page because a reader deciding whether the trade was worth it cannot make
that call from the half of it that flatters the change.

**The same scorer also reports a stricter reading of this run, and it is 4.2 points lower.**
`result.json` has carried both from the first round: the `micro` aggregate above, and a
`strict_micro` one that counts 141 further labels as missed — F3 **57.0**, recall **0.5623**, on
the identical 1070 true positives and 561 false ones. `micro` is what is quoted here because it is
the aggregate RealVuln's own published baselines are quoted in, and comparing against them in a
different metric would be comparing two different things. But a stricter figure sitting in the
committed raw output and named nowhere in the prose is exactly the omission this page exists to
prevent. So: the honest range for this run is **57.0 – 61.2**, and 57.0 is the one to use for any
purpose other than comparing against the baselines below.

Held to `result.json` by check 43 as of this round, and it needed to be. The round that raised
the headline updated the range and left the sentence above it holding the *previous* round's
strict figures — two numbers four lines apart, disagreeing, in the passage whose entire purpose is
that the unflattering reading does not get quietly dropped. Check 27 covered every other figure on
this page and not this one, which is how a page that is 95% derived grows a typed number in the
one paragraph nobody would think to doubt.

Every column is the same corpus, the same scorer and the same clone, and the ground-truth digest
is recomputed every round: `sha256:af5901bf…`, unmoved since the first, so nothing shifts
underneath the comparison. The previous engine is re-scored on the checkout before anything
changes, which is what makes each movement attributable to the engine — and this round is the one
where that step finally caught something, in the scorer rather than in the engine. See
**Re-measured** above.

**This round removed 61 false positives and lost no true positive at all.** It answered one
question the pack had never asked of itself: *is this rule about text that is in the file, or
about behaviour the application performs?* A test that calls `os.remove` on its own temp file,
disables TLS verification against a local stub, or hashes a fixture with MD5 is not the
application doing any of those things — but a credential is committed whatever directory it sits
in, so the shape-based secret rules keep scanning everything and only the keyword-guessing one
does not. The seeder was added to the same list as the tests for the same reason: across 62
repositories, `management/commands/seed*.py` and its equivalents held **36 false positives and
not one true positive**, all of them the same `DEMO_PASSWORD` line. And `@csrf_exempt` on a
handler the framework has already restricted to GET is the correct annotation on a read-only
endpoint rather than a hole — 11 more, again with no true positive among them.

Recall did not move, which is the point: 600 true positives before and after.

**The round before this one removed 143 false positives against 45 true positives added** —
precision moved 0.542 → 0.653, the biggest single jump in the project's history and
three times the size of any previous round's. It came from asking a question no rule had asked:
*whose code is this file?* A vendored front-end bundle copied into `static/` is somebody else's
release, and every finding reported in one is addressed to the wrong maintainer. Three rules were
scoring zero true positives on this corpus and were, essentially in their entirety, reports about
jQuery and Bootstrap. The filter costs exactly one true positive — a labelled flaw inside minified
jQuery 3.2.1, at column forty thousand of a single line — and that is the correct trade rather
than a regression: nobody patches a vendored bundle in place, they upgrade the dependency, which
is a different tier's finding.

The rest is recall, and it came from reading labels rather than predicting them. `xss` **11 → 47
of 98**: 39% of its labels sit in a `.html` or `.jinja2` template and no detector had ever named
a template extension, so the engine reported on the view that *builds* a response and never on the
document that renders it. `sql_injection` **11 → 36 of 71**: JavaScript, PHP, Java and C# each had
a SQL-concatenation pattern rule and Python — the one language this number is measured on — had
none, so the class rested entirely on the taint tier, which needs a path rooted in `request.*`;
most of the missed labels are a handler that takes the value as an ordinary parameter and builds
the statement from it. That rule scored 33 TP / 4 FP on its own. `hardcoded_credentials` **6 → 16
of 52**: the pack owned a rule for `SECRET_KEY = os.environ.get("KEY", "fallback")` and had none
for `SECRET_KEY = "literal"`, which is the larger shape by a wide margin.

`other` moved **229 → 228**. That is the jQuery true positive, and it is stated here rather than
netted off against the gains.

## The number stopped being blind, and that matters more than its size

**12.5 and 13.3 were blind measurements.** The engine had never seen this corpus; the score
said what it did on unseen code.

**Neither 24.6, 26.0, 30.9, 31.5, 35.8, 35.9, 39.3, 39.2, 41.6, 59.5, 59.7, 60.5, 61.1 nor 61.2 is.** The rules added between 13.3 and 24.6 were chosen by
reading this benchmark's own false negatives — *which* standard rules were missing was learned
from its labels. The two analyses added between 24.6 and 26.0 were chosen the same way, and the
round after went further: the labelled code itself was read to work out what shape the misses
had. Every rule added is one any SAST ships (weak PRNG for tokens, cookie flags, CSRF
exemptions, a committed fallback signing key, debug-on-by-default, open redirect, NoSQL
injection, credentials in logs, catastrophic backtracking, unauthenticated state-changing
endpoints), so none of them is a pattern reverse-engineered from a particular fixture — but the
*selection* was informed by the corpus, three times now. That is the same category of advantage
`eval/scorecard.md` has always disclosed about the fixture corpus, and it applies here with
more force each round.

**Two movements here are exceptions, and they are worth stating precisely, because they are the
parts a blind run would also have produced.** The 30.9 → 31.5 round added no rule and read no
label: it removed a bug in an existing one, found by noticing that the branches which suppress a
finding had no test coverage. And the largest component of the 31.5 → 35.8 round — the 143 false
positives removed by the vendored-asset filter — was not selected against this corpus either. A
minified bundle is not application source anywhere; the corpus revealed how *much* that was
costing, not that it was wrong. The two recall gains in the same round (`xss`, credentials) were
corpus-informed in the usual way and carry the usual discount. Neither exception makes the
cumulative number blind again — every rule underneath it was still selected against this corpus.

So read 61.2 as "what the engine does on a corpus it has been tuned against across four
rounds", and read 12.5 as "what it did on a corpus it had not". The honest successor to a blind
number is a run against a benchmark this repository has not read; until there is one, the blind
figure in the right-hand column is the more conservative claim about your code. **The gap
between 12.5 and 61.2 is the size of the advantage this disclosure is about, and it has widened
every round.**

**The deterministic tier scores above rule-based SAST's published 17.7, on both metrics** —
1.9x the recall and 3.5x the precision — having been below it on the two earliest runs. Read
that against the section above: the earlier comparison was blind and this one is not, so the

It is now **above** the general-purpose LLM row (51.7) as well, and that is the comparison to be
most careful with rather than the one to celebrate: **those two baselines were measured the way
ours no longer is.** A model given this corpus for the first time scored 51.7; this engine scored
12.5 the first time it saw the corpus, and 59.5 after four rounds of reading its false negatives.
The purpose-built system's 73.0 is still ahead. The honest sentence is that a deterministic
engine tuned against a corpus beats an untuned model on that corpus, which says something real
about what rules can reach and nothing at all about unseen code — the blind figure is still 12.5,
and the SecBench.js sealed slice exists because that gap is the one worth measuring.

Three things this does *not* say. It is not a measurement of the LLM tier, which is the tier
meant to reach the classes below that Tier 0 structurally cannot. It is not a measurement of the
JavaScript engine. This corpus is Python-only, so **read every figure on this page as a statement
about Python.** That gap is no longer unmeasured: [`eval/secbenchjs/`](../secbenchjs/) scores the
JavaScript side against 600 real npm vulnerabilities and reports **recall 0.3735** — and
**0.2234 on its blind first run**, which is the figure to quote for unseen code. The two
numbers are not comparable in either direction and neither page pretends otherwise — this corpus
is applications and that one is libraries, and a library has no request handler for the taint
tier to root a path in. And it is not a claim about your repository: the
half of this corpus labelled `other`, `broken_access_control` and `missing_auth` is still where
most of the misses are, and no pattern added here touches them.

### Round five — no new rule, one rule made honest

The previous four rounds all worked the same way: read the labelled misses, find the shape they
share, build the smallest thing that decides it. This one did not read a label. It came from
asking a question about the *tests* instead — why did the rate-limit rule's suppression branches
have no coverage? — and the answer was that they were wrong, in three ways that all pointed the
same direction: the rule was silent on code it existed to report.

- **A limiter anywhere silenced everywhere.** `_module_has_limiter` walked the whole tree, so
  one `@limiter.limit("5/minute")` on `/login` protected an unlimited `/admin-login` in the same
  file. "Most endpoints are limited and one was forgotten" is the realistic shape of this bug and
  the rule could not see it. Module-level now means module-level: imports, and statements written
  at module scope including the `if not settings.TESTING:` that real app setup is guarded by —
  not function bodies.
- **`attempt` was matching the wrong half of the problem.** It was a limiter marker on its own,
  so `db.record_attempt(email)` in a failure branch read as protection. Writing the break-in down
  is what an unprotected endpoint does *instead* of bounding it. An attempt count is now evidence
  of a limit only where something is compared against it — `attempts_for(ip) > 5` and
  `if too_many_attempts(email)` still silence the rule, `log.warning("failed login attempt")`
  no longer does.
- **+10 TP for +6 FP, precision 0.5405 → 0.5419.** Small, contained entirely in `other`, and
  accepted only because precision rose. The same edit with precision falling would have been
  reverted under the rule the round before last established.

### Round four — three more structural rules, and one of them is the largest single gain yet

The method was the same one that worked in round three: read the labelled misses, notice what
shape they share, and build the smallest thing that decides it. What the labels showed was that
three of the biggest untouched pools are not judgement calls at all — they are properties of a
handler that a parser can check.

- **Missing rate limiting: 0 → 85 true positives at 0.842 precision.** The largest single-rule
  gain in the project. 99 labels across four related classes named a missing rate limit and the
  engine found none of them, because "this endpoint has no limiter" describes almost every
  endpoint in almost every application. The labels are narrower than that: the flaw is that a
  **credential-testing** endpoint accepts unlimited attempts. So the rule fires only where the
  path or handler names an authentication action *and* the handler actually reaches a credential
  check — and it looks for a limiter in the decorators, the dependencies, module-local helpers,
  and anything registered on the app, because a limiter installed as middleware protects handlers
  that never mention it.
- **Unrestricted upload: 0 → 8, at 0.800 precision after one correction.** An upload is read, a
  write happens, and no check stands between them. The first version scored 8 TP against 14 FP;
  twelve of those false positives were not handlers at all — a test module, a password-list
  generator — matched because `.filename` is an attribute plenty of objects have. Anchoring the
  attribute to a request read removed all twelve.
- **Mass assignment: 0 → 1.** Effectively unmoved, and the reason is worth stating: the corpus's
  mass-assignment labels mostly pass the body through a helper that *is* named like a validator
  (`validate_update_form`) while not actually restricting fields. This rule judges whether a field
  allowlist is present, never whether it is adequate, so those are outside what it decides. That
  is a bound, not a bug, and it is in `limitations()`.

**Precision rose with recall for the third consecutive round: 0.511 → 0.540.** Eighty-six more
true positives against twenty-six more false ones.

### What the rules cost to get right

Two corrections were measured rather than reasoned about, and both are now tests:

**`splitext` is not validation.** Treating extension *extraction* as an extension *check*
silenced the one handler that splits the extension off precisely so it can keep it on the file it
writes. Removing `splitext` and `suffix` from the validation markers recovered that finding.

**The structural rules are scoped to production sources.** Every rule in the package describes
something a *deployed handler* fails to do, so a test module, a fixture, a migration or a
one-off script is out of scope by construction. The detector pack still scans those files — a
committed secret in a test is a real secret — but "this endpoint has no rate limit" is not a
question a test file can answer.

### An honest ceiling on all four rules

They are AST-based, so a **Python 2 source does not parse and produces nothing**. The corpus
contains such files, and at least one labelled upload lives in one. Nothing is guessed there.

### What still does not move

`broken_access_control` (2/76) and `missing_auth` (7/74) moved this round for the first time, and moved by three labels between them — which is progress and not a solution. **`path_traversal` was
on this list for four rounds and is not any more** — 3/39 → 22/39 once `pathlib` was modelled;
what kept it here was a wrong diagnosis, not a hard class, and the section below says so.
`sensitive_data_exposure` (31/141) and `security_misconfiguration` (39/108) are unchanged too, and
reading their misses explains why: about 130 of those labels sit on a `def` line, meaning the flaw
is a property of what the whole handler returns or configures rather than of anything in it. That
is the same shape as broken access control, and the same answer applies — it needs the
business-logic pass, not another rule.

## Reproduce it

```bash
git clone https://github.com/kolega-ai/Real-Vuln-Benchmark
cd Real-Vuln-Benchmark && python3 clone_repos.py && cd -

python3 eval/realvuln/run.py --benchmark ../Real-Vuln-Benchmark

cd ../Real-Vuln-Benchmark
for r in repos/*/; do python3 score.py --repo "$(basename "$r")" --scanner secaudit; done
python3 dashboard.py --scanners secaudit
```

Six practical notes, so the next run does not rediscover them:

1. `score.py` takes `--repo` and scores one repository at a time. The `--all-repos` flag this
   file used to document does not exist.
2. On Windows it aborts writing its own markdown report under a non-UTF-8 console codepage —
   `PYTHONUTF8=1` in front of the command is enough.
3. **Scoring a second scanner overwrites the per-repo scorecards** for the same date. Capture
   what you need from `reports/` before scoring the next one, or score them in the order you
   intend to read them.
4. **`compute_gt_hash.py` disagrees with the published digest on Windows, for an identical
   corpus.** It hashes raw file bytes and joins paths with `os.sep`, so a CRLF checkout and
   backslash separators each change the result. Normalise line endings to LF and use forward
   slashes and it reproduces `sha256:af5901bf…` exactly. This matters more than it looks: the
   first reading says the ground truth moved, which would mean no run is comparable to any
   other.
5. **Do not `rm -rf scan-results/` between runs — it silently deletes the strict denominator.**
   `dashboard.py` builds its repo grid from the directories under `scan-results/`, and
   `strict_micro` is the reading where a repository with no scorecard contributes *all* of its
   labels as misses. The four repositories that are gone from GitHub have no results and are
   supposed to be in that grid as empty directories; delete them and `strict_micro` collapses
   into `micro`, the published range **57.0 – 61.2 quietly becomes a single number**, and the
   figure that goes up is the flattering one. Recreate the four (`realvuln-owasp-web-playground`,
   `realvuln-pygoat`, `realvuln-python-app`, `realvuln-vulnerable-api`) as empty directories
   before running `dashboard.py`, and check `repos_total` reads 66 rather than 62 in the output.
6. **Re-measuring a round that is not committed yet takes `collect_result.py --amend`.** Without
   it the script pushes the current head onto `previous_runs` on *every* call, so collecting the
   same round a second time — which is what happens whenever a fix lands and the corpus is
   re-run — leaves a save point in the history wearing the *previous* round's label. It happened
   three times before it was named. `--amend` replaces the head and leaves the history alone;
   check 39 catches the duplicate label if it is forgotten anyway.

Anything under `kit/secaudit_core/` changes the engine digest, **including a comment or a
docstring**. The digest is a hash of bytes, not of behaviour, so editing a docstring after a
corpus run and before collecting its figures stamps the result with code that never produced it.
Check 32 catches it, and the fix is to finish every edit under `kit/secaudit_core/` first and
run the corpus last.

`run.py` only writes `scan-results/{repo}/{scanner}/results.json` in Semgrep JSON, which
RealVuln ingests without a custom parser. It computes nothing: **the benchmark's own scorer is
the authority.** A tool that grades itself against someone else's corpus has reintroduced
exactly the problem the corpus was there to solve.

## The LLM tier has no number, and here is the command that would produce one

Every figure on this page is Tier 0. That is not an oversight and it is not modesty — Tier 0 is
the part that reproduces: same corpus, same engine, same number, on any machine, with no key.
A model run is not that.

But "not reproducible" has been doing too much work as an excuse. The LLM tier is the front
page's headline claim — triage, verification, the logic bugs the deterministic tier structurally
cannot reach — and a headline claim with no measurement behind it is exactly the kind of thing
this repository refuses to accept from anyone else. So the measurement is now one command:

```bash
python3 eval/realvuln/run.py --benchmark ../Real-Vuln-Benchmark     --backend anthropic --scanner secaudit-tier1
cd ../Real-Vuln-Benchmark
for r in repos/*/; do python3 score.py --repo "$(basename "$r")" --scanner secaudit-tier1; done
python3 dashboard.py --scanners secaudit-tier1
```

Two guardrails are built into that path. `--backend` refuses to write under the plain `secaudit`
slug, because that slug is what `result.json` and every published figure mean and a model run
must never be mistaken for them. And the run prints its own caveat before it starts.

**It has not been run.** No key was available on the machine that built this, and rather than
publish a number from a model nobody can re-query, or quietly leave the tier unmeasured, the
harness ships unrun and this paragraph says so. When it is run, the result belongs on this page
labelled as a single observation — the honest shape for a number that cannot be a floor.

Two things to expect when someone does run it. It costs real money across 62 repositories. And
the comparison it invites is with the published general-purpose-LLM baseline (F3 51.7), which is
the row this tier exists to compete with — not with the 61.2 above.

## Reading the result honestly

- **RealVuln v1 is Python-only** (Flask, Django, FastAPI and friends). SecAudit's Python taint
  analysis runs on a real AST; its JavaScript/TypeScript analysis is a hand-rolled scanner.
  A Python score does not transfer to the JS side, in either direction.
- **Tier 0 only.** `run.py` passes `--no-deps --no-scanners`, so the number describes the
  deterministic, dependency-free engine — the part that is reproducible. If a Tier 1 number is
  ever published it will be labelled as a separate, non-reproducible run.
- **Several of the corpora are deliberately vulnerable teaching apps** (DVPWA, VAmPI and
  friends). They are denser in planted flaws than production code, which flatters recall and
  punishes precision relative to a real repository.
- **The committed 0.986 F3 on our own fixtures and the 12.5 here are not in
  conflict, and neither one is the lie.** The first is a regression floor over a corpus written
  alongside the detectors; the second is what that engine does on code nobody here has seen.
  A repo that publishes only the first is marketing; a repo that publishes only the second has
  thrown away its regression gate.
